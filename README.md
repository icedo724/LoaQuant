# 로스트아크 경제 시계열 분석

## 주요 거래품목 시세 분석
GitHub Actions를 활용해 로스트아크 경매장의 주요 품목 최저가를 **1시간 주기**로 자동 수집하고 시각화합니다.

### 자동 가격 수집 대상
1. **T3/T4 강화 재료**
2. **생활 재료**
3. **배틀 아이템**
4. **유물 각인서**
5. **T4 8레벨 이상 보석**

### 수동 업데이트
- 골드 가격 (100골드당 원)

  현재 이 값은 사람이 Discord 채팅 로그를 직접 내보내야 갱신된다
  (`common/gold_extract.py` → `common/gold_processing.py` → `data/gold/daily_gold.csv`).
  로스트아크 오픈 API 에는 크리스탈 거래소·환율 엔드포인트가 없어 공식 경로로는
  자동화할 수 없다. 갱신이 멈추면 환산값이 조용히 낡으므로, 읽는 쪽에서 신선도를
  확인해야 한다.

### 서비스 링크
수집된 데이터는 Streamlit을 통해 대시보드에서 실시간으로 확인할 수 있습니다.

- **[LoaQuant 바로가기](https://loaquant.streamlit.app/)**

- **[대시보드 기능소개](https://www.notion.so/miniminimin/LoaQuant-325fbcdaed2880b18277ddcee3881459?source=copy_link)**

### 주요 기능
**1. 시세 추적**
- 1시간 단위 실시간 최저가 흐름 차트 제공
- **로아 서버 기준(매일 오전 06시)** 으로 정산된 일평균 가격 제공
- 전일 대비 등락폭 및 가격 변동 표시

**2.  시장 분석**
- **RSI (상대강도지수)** 및 **볼린저 밴드**를 활용한 통계적 분석
- **과매수(고점)/과매도(저점)** 구간 탐지
- 직관적인 시장 분석 리포트 카드 UI 제공
- 현금 가치 확인 기능 제공


**3. 시각화 및 유틸리티**
- **정기 점검 시각화**: 매주 수요일 점검 시간(06:00~10:00) 차트 내 회색 영역 표시
- **이벤트 추적**: 주요 이벤트 종료 일자 그래프 내 마킹
- **교환 효율 계산**: 하위 재료 ↔ 상위 재료 교환 시 손익(골드 가치) 자동 비교 분석
- **패치분석실**: 시계열 모델 기반 비정기적 요인에 대한 영향 시각화

## 데이터 수집 정책

로스트아크 오픈 API의 호출 한도는 **분당 100회**다. 수집기는 이 한도 아래에서 동작하도록
`common/api_client.py` 한 곳에서 호출 간격과 재시도를 통제한다.

| 항목 | 값 | 근거 |
|---|---|---|
| 호출 간격 | 분당 95회 (요청당 0.63초) | 한도 100회에 안전 여유를 둔 값 |
| 잔여 할당량 | `X-RateLimit-Remaining` 이 10 미만이면 리셋까지 대기 | 같은 API 키를 다른 곳에서 함께 쓰면 고정 간격만으로는 실제 잔량을 알 수 없다 |
| 재시도 | 최대 4회, 지수 백오프 (5→10→20→40초) | 고정 간격 재시도는 한도를 계속 두드리게 된다 |
| `Retry-After` | 서버가 지정한 값을 그대로 대기 | 상한으로 자르면 지시보다 일찍 재요청하게 된다 |
| 대기 상한 초과 | 재시도하지 않고 해당 요청 포기 | 일찍 두드리는 것보다 포기가 낫다 |
| 연속 실패 | 5건 누적 시 수집 중단 (부분 데이터는 저장) | API 응답 불가 상태에서 수백 건을 계속 시도하지 않는다 |
| 동시 실행 | 두 워크플로가 같은 `concurrency` 그룹 | 실행이 겹치면 같은 키로 동시 호출해 한도를 초과한다 |
| 실행 시간 | 시세 `timeout-minutes: 15`, 거래량 `20` | 시세 정상 실행은 약 1분이다 |

잔여 할당량 제어는 **더 느리게 만드는 방향으로만** 동작한다. 잔량이 넉넉하다고 해서
고정 간격보다 빨리 보내지는 않는다. 헤더를 믿고 간격을 좁히면 헤더가 누락되거나
부정확할 때 곧바로 한도 위반이 되기 때문이다.

### 수집 주기

| 워크플로 | 주기 | 1회 요청 수 | 소요 |
|---|---|---|---|
| `main.yml` (시세) | 매시간 목표, 크론은 `13,33,53 * * * *` | 약 97건 | 약 1분 |
| `volume.yml` (거래량) | 하루 1회, `17 20 * * *` (KST 05:17) | 약 120건 | 약 1.5분 |

크론이 정각이 아닌 이유는 GitHub 이 스케줄 이벤트를 최선노력으로만 보장하기 때문이다.
정각은 가장 혼잡한 슬롯이라 이벤트가 자주 버려진다. 실행 기록 60건을 확인했을 때
모든 런의 `run_started_at - created_at` 이 0분이었다. 큐에서 밀린 것이 아니라
이벤트 자체가 발생하지 않은 것이므로, 대응은 시도 횟수를 늘리는 것뿐이다.

시도가 늘어난 만큼 과수집은 `economy/collect_guard.py` 가 막는다. 마지막 수집으로부터
50분이 지나지 않았으면 그 실행은 종료한다. 기준이 60분이 아닌 이유는 크론이 `:13/:33/:53`
에 뜨므로 성공 시각이 정확히 1시간 간격이 아니기 때문이다.

거래량은 일 단위 데이터(`Date` + `TradeCount`)이므로 하루 1회면 충분하다. 응답에 최근
여러 날치가 함께 오고 저장은 `combine_first` 병합이라, 하루 이틀 놓쳐도 다음 실행에서
메워진다. 아이템 ID 는 시세 수집이 남긴 `data/item_id_map.json` 에서 읽는다. 예전에는
ID 를 얻으려고 같은 검색 요청 81건을 다시 보냈는데, 그 응답은 시세 수집이 이미 받았던
것과 동일했다.

실행 결과는 `data/collection_log.csv` 에 한 줄씩 남는다. 수집이 안 된 시각은 CSV 에서
존재하지 않는 컬럼이라 결측인지 아닌지 구분할 수 없으므로, 실행 자체를 기록해 주기를
모니터링한다.

정책이 깨지면 곧바로 이용 한도 위반이나 과수집으로 이어지므로 검증을 붙여 두었다.

```bash
python tests/test_api_client.py   # 호출 한도·재시도 정책
python tests/test_collectors.py   # 멱등성 가드·수집 로그·환율 추출
```
